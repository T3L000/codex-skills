# 任务包交付

把任务包当成交付合同，而不是普通编码提示。围绕任务包完成范围确认、实现、验收、差异审查和证据化交付。

## 强制流程

### 1. 建立交付账本

开始修改前提取并持续维护：

- 目标与用户可观察结果
- 范围、非目标和禁止项
- 验收标准
- 每项验收标准对应的验证方法
- 风险、依赖和待确认假设

优先使用仓库已有的计划或任务文件；没有必要时不要额外制造文档。若歧义会实质改变范围、接口、数据或外部行为，先请求用户决策；否则采用最小假设继续，并在交付时说明。

### 2. 检查基线

读取适用的 `AGENTS.md`、仓库约定和相关实现。检查工作树，保留用户已有改动。确定本次变更的基线、直接调用方、相关测试和最小验证命令。

不得把无关重构、依赖升级或代码清理混入任务包。发现范围外问题时记录，不要顺手修改。

### 3. 实现最小完整增量

按验收标准实现最小、连贯、可验证的变更。每完成一个可测试增量就运行最小相关检查。失败时先诊断证据，再修复；不要用猜测替代验证。

### 4. 执行验收验证

把每项验收标准映射到新鲜证据，例如测试输出、构建结果、静态检查、API 响应或界面观察。

只有当前任务中实际运行并读取过的结果才能作为证据。无法执行的验证必须明确标为未验证，并说明原因、风险和用户可运行的命令。

### 5. 执行差异审查门

审查范围仅包括：

- 任务包及其验收标准
- 相对基线的本次变更 diff
- 受影响的直接调用路径、配置和测试

不要在每轮修复后重新泛化扫描整个仓库。按以下维度审查：

- 正确性与边界条件
- 验收标准覆盖度
- 回归、错误路径和状态一致性
- 与现有架构和约定的一致性
- 与本次变更相关的安全、性能和可维护性风险
- 测试是否真正证明行为，而不只是执行代码

只报告可行动、可定位、可证明的问题。为每个 finding 提供严重级别、文件/位置、失败场景和修复方向：

- `P0`：可能造成安全事件、数据丢失、不可逆破坏或核心功能全面失效；必须阻塞交付。
- `P1`：违反任务要求、产生高概率正确性问题或明显回归；必须阻塞交付。
- `P2`：非阻塞的可维护性、低风险性能或改进建议；记录但不得驱动无限修复。

不要因为个人风格偏好、理论上的完美设计或范围外旧问题制造 P1。

若 `open-code-review-delegate` 或其他仓库级 Review 工具已经可用，并且任务是 Git 变更，可以用它生成候选 findings。必须由当前代理结合任务包和实际代码复核这些 findings；不要盲信或全盘接受工具输出。

### 6. 修复并收敛

默认执行两轮：

1. 第一轮审查完整任务 diff，修复全部确认的 P0/P1。
2. 第二轮只审查修复产生的新 delta、相关回归风险和重新运行的证据。

每次修复后重新运行受影响的验收检查。若第二轮仍有 P0/P1，停止自动循环并报告未解决阻塞项、影响和建议决策；除非用户明确要求，或安全与数据完整性风险需要追加验证，否则不要继续无界 Review。

### 7. 通过完成门

只有同时满足以下条件才可声明完成：

- 所有验收标准均有证据，或明确标注无法验证
- 没有未解决的 P0/P1
- 相关测试、构建和检查使用的是修复后的新鲜结果
- 工作树中的实际 diff 与任务范围一致
- 未处理的 P2、假设和残余风险已明确说明

最终交付按以下顺序简洁报告：完成结果、关键变更、验收证据、Review 结论、残余风险。不要用“应该、看起来、估计”替代证据。

## 禁止模式

- 每修一个问题就重新审查全仓库
- 把所有 AI 建议都当成必须修改
- 为消灭 P2 无限迭代
- 用旧测试结果或其他代理的成功声明证明完成
- 在任务包中混入范围外重构
- 在仍有 P0/P1 时弱化措辞并宣布完成
